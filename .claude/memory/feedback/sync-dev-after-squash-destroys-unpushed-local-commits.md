name: sync-dev-after-squash-merge.sh destruye commits locales ahead-of-main sin pushear
description: Si commiteás cosas nuevas en `dev` local DESPUÉS de `gh pr merge --squash` y ANTES de correr `bash scripts/sync-dev-after-squash-merge.sh`, esos commits SE PIERDEN del backup remoto (force-push de `dev-backup = main` los borra). Quedan solo en local. Si el entorno muere o se hace `reset --hard`, trabajo perdido. Detectado durante una sesión upstream de auditoría (N commits perdidos del análisis intermedio). **Fix aplicado (DT-NNN cerrada · Modo A):** sección 2.6 del script ABORTA si `git rev-list --count origin/main..dev > 0` · smoke `infra-flujo/sync-dev-guards-local-commits-ahead.sh` defiende contra regresión silenciosa en CI lint.
type: feedback
---

Cuando un PR se mergea con `gh pr merge <N> --squash` a `main`, la regla #27 push-and-ci-policy obliga correr `bash scripts/sync-dev-after-squash-merge.sh` **inmediatamente después**. La intención de "inmediatamente" es asumir que **no hay commits locales nuevos sobre dev pendientes**. Si los hay, el script los borra del remoto silenciosamente.

**Why:**

- Detectado durante una sesión upstream que ejecutó `/auditar-dt` paso por paso. Reflog mostró `origin/dev-backup` reseteado al SHA de `main` con `forced-update`, perdiendo N commits (típicamente: archivado log + memoria nueva + test SQL + handoff) que el user había commiteado DESPUÉS del squash y ANTES de correr el sync.
- El hook `.husky/post-commit` SÍ funcionó · cada uno de los 4 commits fue pusheado a `origin/dev-backup` (visible en reflog como `update by push`). Pero el siguiente sync los voló con `--force-with-lease` (push forzado con salvaguarda · aborta si el remoto cambió desde el último fetch).
- El script (línea ~19 según feedback hermano `squash-merge-dev-divergence.md`) declara: *"Aborta si dev tiene commits no mergeados a main (defensa contra pérdida de trabajo)"*. La defensa NO disparó en este caso porque el script probablemente compara `origin/main..origin/dev` (vacío post-squash sin pushear nada nuevo) en lugar de `origin/main..dev` (los 4 commits locales adelantados). Gap real del script.
- Sin esta regla, cualquier sesión que sigue trabajando localmente después del squash + corre el sync más tarde, pierde silenciosamente los commits locales del backup remoto · si el entorno muere o se hace `reset --hard origin/dev` por error, el trabajo se evapora · cero rescate posible.

**How to apply (operación humana mientras el script no esté fixeado):**

- **Regla operativa firme post-squash:** la SECUENCIA correcta es `gh pr merge --squash` → `bash scripts/sync-dev-after-squash-merge.sh` → empezar trabajo nuevo en dev. NUNCA intercalar commits locales entre el squash y el sync.
- **Si ya tenés commits locales encima y no corriste el sync todavía:** NO corras el sync directo. Antes verificar con `git log origin/main..dev --oneline`. Si hay commits, abrir PR nuevo con ellos primero · O respaldarlos manualmente a otra branch (`git branch backup-pre-sync-$(date +%s)`) antes del sync.
- **Auto-chequeo de 3 segundos antes de cada `bash scripts/sync-dev-after-squash-merge.sh`:** ¿hay commits locales en dev que no estén en main? Si SÍ → pausar y rescatarlos primero. Si NO → ejecutar el sync.
- **Recovery si ya pasó:** los commits locales siguen en `dev` local (no se borran de tu disco · solo del remoto). Hacer checkout a dev y commitearlos en un PR nuevo. Backup remoto se restaura solo con el próximo commit (hook post-commit hace force-with-lease si detecta non-FF · `non-FF` = non-fast-forward · push rechazado porque el remoto tiene historia divergente que el push borraría).

**Detección rápida del bug:** después de correr el sync, verificar `git ls-remote origin dev-backup` vs `git rev-parse HEAD` (en dev local). Si difieren, hay commits locales que el sync ya removió del backup. Acción: commit + push (el hook post-commit auto-recupera dev-backup con `--force-with-lease`).

**Fix aplicado (DT-NNN cerrada · Modo A):** sección 2.6 del script verifica `git rev-list --count origin/main..dev` (LOCAL dev) post-fetch · si retorna > 0, ABORTA con mensaje de rescate accionable (push a PR nuevo · backup a branch local con timestamp). Smoke regression-first `tests/scripts/infra-flujo/sync-dev-guards-local-commits-ahead.sh` defiende el invariante mecánico (3 asserts: guard presente · ABORT con `exit 1` · path de rescate visible) · wireado al job `lint` de `local-ci.sh` y `.github/workflows/ci.yml` con severidad ABORT.

**Refinamiento iterativo upstream (firma user · workflow-base):** el fix DT-NNN anterior generaba FALSO POSITIVO en el happy path squash merge. Post `gh pr merge --squash`, `dev` local conserva los N commits del PR con SHAs originales mientras `origin/main` tiene 1 squash commit con MISMO contenido pero distinta historia · `git rev-list --count origin/main..dev` retorna N (los commits "ahead" por historia) y el guard 2.6 ABORTA sin necesidad (cero pérdida real porque el contenido ya está en main). Fix: pre-check tree-comparison ANTES del guard original · compara `git rev-parse "dev^{tree}"` con `git rev-parse "origin/main^{tree}"` · si coinciden → squash detectado → skip el guard con mensaje yellow informativo. Si difieren → guard original aplica intacto (protección DT-NNN preservada para commits locales con cambios genuinos). Smoke regression-first nuevo: `tests/scripts/infra-flujo/sync-dev-pre-check-tree-comparison.sh` (3 asserts · pre-check presente · branching squash · ABORT original intacto) · severidad ABORT en job `lint`. Las dos defensas conviven: pre-check resuelve FP del happy path · guard DT-NNN sigue protegiendo el caso original.

**Refinamiento iterativo upstream · iteración 2 (firma user · post-runtime-test):** el fix inicial cubría SOLO el guard 2.6 (defense-in-depth DT-NNN) pero el script tenía un SEGUNDO guard estructuralmente equivalente en la sección 4 (línea 98 · `ahead_main = origin/main..origin/dev`) que también ABORTABA en el happy path squash con el mismo FP. **Detectado durante test runtime end-to-end** (escenario A: repo aislado en `/tmp/` con squash merge simulado · script ABORTÓ con `ABORT: origin/dev tiene 2 commit(s) que NO están en origin/main` post `Squash merge detectado · skipeando guard 2.6`). Ni N1 (shellcheck/bash-n) ni N2 (Agent fresh) ni el smoke estructural (grep al guard 2.6) detectaron el bug · el test runtime fue el único canal capaz de atraparlo. **Fix complementario:** refactor a variable unificada `SQUASH_DETECTED=true/false` calculada UNA vez ANTES de los 2 guards · consumida como pre-condición en AMBOS (`[ "$SQUASH_DETECTED" = false ] && ...`). Cero duplicación · cero drift entre los 2 guards · mensaje informativo único "Squash merge detectado · skipea guards 2.6.b + sección 4". Smoke actualizado a 4 asserts (tree-comparison primitivas · variable unificada · ambos guards consumen SQUASH_DETECTED). Re-test runtime post-fix: escenario A (happy path squash · debe CONTINUAR) → 4/4 asserts ✓ · escenario B (DT-NNN preservado · commits locales sin squash · debe ABORTAR) → 3/3 asserts ✓. **Lección operativa:** test runtime end-to-end (aunque sea con setup artificial en `/tmp/`) es la única red defensiva contra bugs que las validaciones estáticas + cualitativas no atrapan · scripts con MÚLTIPLES guards estructuralmente equivalentes deben unificar el pre-check para evitar "fix incompleto" silencioso.

**Alternativas descartadas:**

- Confiar en el operador: ya falló al menos 1 vez en sesiones upstream · la regla #27 dice "inmediatamente" pero "inmediatamente" es subjetivo · necesita gate mecánico.
- Hacer el script ignorar dev-backup: pierde la simetría firmada upstream (la otra extensión del feedback hermano que SÍ es correcta cuando no hay commits locales).
- Hook pre-script que pushea automático a un PR: requiere bot + permisos elevados · paridad con la decisión histórica de NO automatizar el sync.
